# Design note: tokenisation service, version 3

This note describes the internal design of our card tokenisation service. Do not share it outside the platform security team.

The service replaces card numbers with random tokens at the edge. Tokens are generated by a keyed pseudorandom function; the key lives in the hardware security module and is rotated every 90 days. The mapping table is stored in a separate database cluster that only the detokenisation service can reach, over mutual TLS with pinned certificates.

Known weaknesses: the rate limiter on the detokenisation endpoint is per instance, not global, so an attacker with a stolen service credential could exceed the intended limit by spreading requests. The fix, a shared counter in Redis, is planned for the next quarter.

The proprietary routing algorithm that picks the cheapest acquirer per transaction is described in appendix B and is the main reason this document stays within the team.
